# AI Factory 一人公司升级与执行方案

日期：2026-09-13  
状态：实施中。P0-1 已实现并通过回归，详见 [项目版本规格](project-versions.md)；其余阶段尚未实现。本文中的商业目标不代表收益承诺。  
目标：把现有网页生成工作台升级为能重复交付、记录成本、支持收费服务的个人业务系统，逐步减少经营者参与。

## 1. 先明确我们要做成什么

第一阶段定位：**你经营一家小型网站交付服务，AI Factory 是内部生产和管理工具。**

先提供一种标准化服务：面向单一行业的展示网站制作与维护。行业暂不锁定，优先选择你能接触到客户、能获取合法素材的领域。暂不同时承接商城、支付、库存、多租户 CRM 等复杂系统。

标准交付范围建议：品牌介绍、服务或产品展示、案例、联系方式、移动端适配、真实域名上线、基本访问检查及操作说明。客户提供或确认事实和素材，系统不能编造客户案例、资质、评价。

第一版联系入口可采用已确认的电话、邮箱或客户已有渠道。只有接入真实接收端并验证送达后，才能把表单计入交付范围。

收入来源候选：一次性制作服务费，以及有明确服务范围的后续维护费。先验证有人愿意付款，再考虑卖 AI Factory 订阅或开放自助建站。

**软件无法保证收入。** 收益取决于客户需求、获客渠道、报价、交付成本和复购。本方案的作用是建立可验证的收费与交付流程，不能用生成数量替代真实收入。

## 2. 当前基础与缺口

| 项目 | 当前情况 | 升级方向 |
|---|---|---|
| 需求、方案与人工审批 | 已有 | 标准服务范围、一次性批量确认 |
| 生成、修复与代码核对 | 已有基础流程 | 项目增量修改、业务测试、失败定位 |
| 本地任务归档 | 已有后端 SQLite 与弹窗 | 客户、项目、版本、交付和成本关联 |
| 生成应用数据 | 可采用本地或演示数据，外部服务支持有限 | 明确真实与演示能力，按服务范围验证 |
| 测试 | 工作台已有自动化测试 | 每个交付项目有独立业务验收证据 |
| 上线与运维 | 尚无完整自动闭环 | 预览发布、生产发布、回滚、健康检查 |
| 获客、报价、收款 | 尚无完整闭环 | 先人工引入少量客户，逐步记录和自动辅助 |
| 经营数据 | 尚无项目实际利润台账 | 工时、模型、托管、返工及实收记录 |

最近 178 项测试是工作台回归结果，不代表生成项目的商业交付成功率。第一笔真实订单之前，不声称商业模式验证成功。

## 3. 你需要参与多少

目标是减少零碎干预，而非无限授权无人经营。首批试单需较多反馈；流程稳定后，以每单例外事件数和人工分钟数衡量改善。

| 环节 | 系统负责 | 你负责 |
|---|---|---|
| 初次设置 | 提供服务套餐、流程与成本模板 | 确认目标客户、服务范围、预算和发布权限 |
| 收集需求 | 结构化整理、检查缺失、合并问题 | 必要时确认客户身份、素材和商业事实 |
| 报价 | 按已确认规则生成报价草案 | 初期确认价格与对外承诺 |
| 制作 | 生成、增量修改、测试、预览、报告 | 只处理无法消除的需求歧义或重大取舍 |
| 交付 | 整理差异、测试证据与交付资料 | 初期确认生产发布；客户确认最终成果 |
| 维护 | 健康检查、备份、诊断和告警 | 决定超范围需求、退款、额外费用等事项 |

默认把需要你处理的问题汇总成一张“待决策清单”，避免逐条打断。未来只有在你明确授权的套餐、预算、目标和发布规则内，才允许自动完成相应动作。

系统可以自动准备客户消息，但不能因为有模板就擅自发邮件、群发营销、承诺价格、开通付费服务或退款。外部动作需要事先约定的授权范围。

## 4. 优先实施：P0——让一个项目能持续交付

### P0-1 客户项目与版本管理

- 区分客户、长期项目、单次执行任务和交付版本；不能把一次任务等同于一个长期项目。
- 在现有任务历史基础上建立关联，保留原始需求、素材引用、范围、验收标准和状态。
- 每次成功修改产生独立版本；失败版本不覆盖上一个可交付版本。
- 提供“继续修改这个项目”，加载现有代码及历史要求，只修改受影响范围。
- 记录变更前后差异、检查结果、版本关联及回退入口。

验收：同一个网站连续修改三次，未修改的内容和已有功能保留；失败修改不会损坏上一版；可以恢复到指定版本。

### P0-2 可恢复执行与异常队列

- 将待执行、执行中、待审批、失败、已中断、已交付分开。
- 保存步骤输入、输出、运行版本、尝试次数和检查点。
- 可安全重试的步骤有限重试；发布等外部动作使用幂等标识，重试前检查实际状态。
- 服务重启后提供恢复或重新执行步骤的明确选择，不能无条件重放操作。
- 同一项目限制并发修改；多进程部署前引入任务租约，避免不同进程争抢任务。

验收：在生成、构建和等待审批时分别中断服务，恢复后无重复发布、无重复审批执行、无项目版本混乱。

### P0-3 真实交付模式与业务测试

- 新增“演示”和“交付”模式。交付模式禁止把模拟数据、假成功提示和未接通接口作为已实现能力。
- 将原始要求映射为可操作的验收项，记录实际结果、截图和日志。
- 展示站基线：页面可达、导航有效、移动端无关键遮挡、素材无失效、链接正确；表单存在时必须验证接收结果。
- 测试包含失败场景，不能只有首页截图和 npm build。
- 未验证、依赖缺失和不支持的能力明确阻止交付，不由模型自行宣称通过。

验收：故意制造坏链接、错误联系信息映射、提交失败和移动端遮挡，测试应识别相应故障；修复后保留再次验证证据。

## 5. P1——让交付有成本边界并能上线

### P1-1 模板与固定服务套餐

- 先维护一个行业、两套可复用展示站模板；不追求大量模板。
- 套餐描述交付页面、支持能力、所需素材、修改范围和不包含的内容。
- 将客户差异限制在内容、品牌和有限配置，减少每次从零生成。
- 修改范围外需求生成追加工作草案，不能自动无限返工。

验收：三个不同客户资料能复用同一模板交付，客户内容不互相泄露，公共修复有回归测试。

### P1-2 成本记录与预算停止

- 记录模型实际 usage；供应商未返回时标记估算，不能伪装成实际费用。
- 记录生成、修复、测试与部署耗时，人工沟通和修改时间，以及托管、素材等支出。
- 配置每任务调用次数、修复次数、超时与费用预算；达到上限进入待决策状态。
- 模型价格使用可更新配置并记录计价版本，不在代码里假设永久不变。
- 对账前区分估算费用、供应商实际账单和实收款。

验收：模拟连续失败，任务在预算或重试上限处停止；报告解释成本来源，未知费用明确标记。

### P1-3 发布、备份和回滚

- 先选定一个部署目标，避免同时建设多云发布。
- 生成代码在受限执行环境中构建，限制运行时间、可访问目录和凭据。
- 先发预览环境，通过测试和授权后发布生产版本。
- 记录域名、部署版本、健康检查和上一可用版本；发布失败保留旧站。
- 数据库迁移与代码回滚分开处理，有业务数据时必须设计备份与兼容策略。

验收：完成一次真实预览发布、一次生产发布和一次故障回滚演练，验证旧版本能访问。未经授权的目标和预算不能发布。

## 6. P2——建立可收费的经营流程

### P2-1 客户与订单台账

- 流程：线索 → 需求确认 → 报价 → 付款状态 → 制作 → 客户验收 → 交付 → 维护。
- 第一版允许人工确认付款并关联凭证，不急于接入复杂支付系统。
- 保存服务范围版本、约定修改次数、交付日期、客户反馈与实收金额。
- 报价和交付资料由系统起草，按授权规则对外发送。
- 多客户隔离资料、代码、密钥和访问链接。

### P2-2 维护与少打扰

- 定期检查线上可达性、关键流程与备份结果。
- 可重复验证的轻微故障可以自动诊断和准备修复；涉及数据或商业行为的变更按授权处理。
- 正常运行不频繁通知，异常汇总到待处理队列；严重故障及时提醒。
- 每周报告：新订单、实收、成本、返工、人工时间、线上异常。

### P2-3 服务器迁移

- 当前继续使用本机后端 SQLite，不将正式数据迁移到浏览器存储。
- 在代码中抽象存储接口，把绝对生成路径逐步改为可迁移的项目/版本引用。
- 服务器单进程初期可评估继续使用 SQLite；需要多实例和并发任务时再迁移 PostgreSQL 及独立任务队列。
- 上云前补齐登录、访问控制、密钥管理、备份恢复和执行隔离，不能直接公开现有 localhost 服务。
- 迁移前后核对记录数量、关联关系、生成文件校验值，并演练恢复。

验收：清空浏览器缓存后历史仍完整；换机器恢复后任务、版本和文件关联正确；客户之间不能读取彼此资料。

## 7. 用真实试单验证，而不是继续无限开发

以下是内部试验门槛，不是行业成功率、市场报价或收入预测。

1. 获取三个真实潜在客户的需求，确认他们现有问题、替代方案和付费意愿；由你提供联系人或明确授权沟通范围。
2. 从中选择一个范围明确、可验收的付费试单。没有付费意愿时先调整服务，不继续堆功能。
3. 使用 AI Factory 从需求到上线走完一单，记录所有人工介入和故障。
4. 交付后观察一个约定周期，例如七天，确认实际使用、问题与维护负担。
5. 完成首单后，再验证三单同类服务的重复性；不从一个案例推断可规模化盈利。

| 指标 | 记录口径 | 用途 |
|---|---|---|
| 实收 | 实际收到的款项，退款单列 | 区分订单意向与收入 |
| 直接支出 | 模型、部署、素材、支付等实际支出 | 计算现金贡献 |
| 人工投入 | 沟通、审批、修复、交付、维护的分钟数 | 检验是否减少你的参与 |
| 返工 | 次数、原因、是否超范围 | 改进模板与报价 |
| 交付稳定性 | 验收通过、线上故障、回滚记录 | 判断能否继续接单 |

单项目现金贡献 = 实收 − 退款 − 直接支出。  
单项目经营价值估算 = 现金贡献 − 人工小时 × 你设定的小时成本 − 分摊固定成本。

税费及其他适用支出需要按实际情况计入；不能把上述简化估算当作净利润。维护费用按真实服务周期分摊。

只有当同类订单有正向贡献、维护可控、人工参与下降，才继续扩大客户数量。若持续亏损，应缩小范围、调整价格或更换服务。

## 8. 下一步具体工作指示

**下一次开发只执行 P0-1：客户项目与版本管理，以及在同一个项目上继续修改。**

建议按以下顺序形成独立可审查提交：

1. 设计项目、执行任务与版本的数据结构，并给现有归档提供可回退的数据迁移。
2. 扩展后端接口，提供创建项目、查询版本、基于指定版本提交修改的能力。
3. 扩展生成输入：现有源码、原始约束、新增变更要求；禁止无依据重写整个项目。
4. 独立保存候选版本，通过检查后才成为当前可用版本。
5. 本地任务弹窗加入项目关联、“继续修改”和版本详情，保持主页面简洁。
6. 编写连续修改、失败保留旧版本、路径越界和版本恢复测试。
7. 用一个真实范围的展示站演练，展示修改前后差异及测试证据。
8. 更新文档、提交分支并推送 GitHub；不自动合并或对外发布。

完成 P0-1 后再执行 P0-2、P0-3，随后开展试单准备与 P1。暂缓首屏装饰、更多光标效果、多模型角色扩张和复杂经营大屏。

你需要先确定的最少信息：目标客户类型、首个可验证需求，以及模型/托管预算上限。若尚无客户，可先做内部交付演练，但必须标注“未验证收费”，不能当作商业成果。
