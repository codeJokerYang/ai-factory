# ADR-002: L3 使用版本化、质量门控制的案例 JSON

- **状态**: 已采纳
- **日期**: 2026-07-20
- **决策者**: 项目维护者 / Codex

---

## 背景

L2 已提供受控的通用方案模板。L3 需要从成功项目中复用更具体的架构经验，但直接扫描所有 wiki
Markdown 无法可靠区分 Gate 1 已批准、最终成功、草稿和项目自身文档；直接复用代码还会扩大安全、
版权、过期实现和 prompt 污染风险。

## 决策

采用独立的 `KnowledgeCase` JSON 作为 L3 信任边界：

- 仅在 build、Reviewer、Security、Gate 2 全部通过后创建或更新。
- 使用 `schema_version` 做兼容性校验，使用项目名 SHA-256 摘要构造文件名。
- 只保存脱敏后的产品摘要和架构摘要，不保存代码、用户故事、目标用户或原始 prompt；读取时再次脱敏，避免人工编辑绕过写入规则。
- 在仓库内 `wiki/knowledge/projects/` 持久化，和代码一起接受 Git review。
- 使用无 token 的词项相似度检索，L2 未命中时最多向 Builder 注入一个 L3 案例。
- 缓存属于优化层；读取或写入失败不得改变主流水线的成功结果。

## 考虑的选项

### 选项 A: 每次扫描 specs/ 与 decisions/ Markdown

- 优点: 不增加新格式。
- 缺点: 难以证明项目最终成功，模板文档和草稿容易混入，解析格式脆弱。

### 选项 B: 版本化案例 JSON（采用）

- 优点: 信任条件明确、字段最小、可校验、可脱敏、可测试、便于版本控制。
- 缺点: 与人类可读 wiki 产物存在少量重复；schema 升级需要迁移或兼容读取。

### 选项 C: embedding + 向量数据库

- 优点: 语义召回更强，适合大量案例。
- 缺点: 增加服务、凭据、成本和数据治理面；当前案例规模不需要。

## 后果

### 正面影响

- 未通过完整质量门的项目不会污染跨项目知识。
- 案例 diff 可由人审查和回滚，且不包含生成代码。
- L2、L3 都是确定性零 token 检索，只增加命中后的有限 prompt 上下文。

### 负面影响 / 风险

- 词项检索可能漏掉措辞差异大的相似项目。
- 只有同时运行 `--verify --gate2` 的成功项目会沉淀，早期案例数量可能较少。
- 脱敏规则只能覆盖已知模式；案例仍需纳入 Git review 和敏感文件检查。

## 迁移计划

未来如果案例数量和漏召回率需要向量检索，保留 `KnowledgeCase` 作为规范数据源，在其上建立派生索引；
不得绕过质量门直接索引原始代码或未批准产物。
