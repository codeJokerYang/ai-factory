# ADR-001: L2 先采用内置只读模板注册表

- **状态**: 已采纳
- **日期**: 2026-07-20
- **决策者**: 项目维护者 / Codex

---

## 背景

`COST_OPTIMIZATION.md` §7 规划了 L2 方案模板和 L3 跨项目知识库。当前流水线已经能生成、
审查和验证应用，但直接复用历史生成代码会带来过期实现、敏感数据传播、错误放大和缓存失效等
问题。第一步需要先建立低风险、可测试的模板命中接口。

## 决策

L2 v1 使用代码内的不可变模板注册表：

- 模板仅包含简短工程约束，不包含可执行代码或项目数据。
- 使用 Product Spec 的结构化字段做确定性关键词匹配，不额外调用 LLM。
- 英文关键词要求完整词边界；所有文本先做 Unicode NFKC 与大小写规范化。
- 最多注入两个得分最高的模板，未命中时不改变现有 Builder prompt。
- 匹配、排序和渲染集中在 `orchestration/template_cache.py`，Builder 只负责调用。

## 考虑的选项

### 选项 A: 把模板规则直接写进 Builder prompt

- 优点: 改动最少。
- 缺点: 每次调用都消耗全部模板 token，无法测试命中逻辑，也难以独立演进。

### 选项 B: 内置只读注册表（采用）

- 优点: 零外部 I/O、零额外 LLM 调用、结果稳定、便于审查和测试。
- 缺点: 新模板需要代码评审，暂时不能从成功项目自动学习。

### 选项 C: 立即建立跨项目持久化缓存

- 优点: 可复用真实产物，潜在节省更多 token。
- 缺点: 需要先解决脱敏、质量评分、版本、失效、并发写入和错误污染，超出本次优化边界。

## 后果

### 正面影响

- 常见场景只注入相关约束，避免通用 prompt 持续膨胀。
- 匹配不依赖模型，离线测试可覆盖完整行为。
- 后续 L3 可以复用 `TemplateMatch`/渲染接口，而无需改 Builder 主流程。

### 负面影响 / 风险

- 关键词仍可能漏命中；新增宽泛关键词可能造成误命中。
- 内置模板不会自动吸收项目经验，需要按运行手册人工维护。
- 当前没有持久化命中率指标，成本收益需要后续可观测性工作验证。

## 迁移计划

如实现 L3，应保持 L2 为高优先级受控来源；L3 内容必须经过脱敏、版本校验和成功质量门，再以
相同的精简 context 接口注入。
